# Security model (Phases 2 to 5)

The admin is **public code**. Anyone can read its JavaScript at `/admin/`; that is by design and nothing in it is secret. What protects the site is GitHub's authorization: only a holder of a valid token for this repository can change anything. This page says what the design protects, what it does not, and which parts were tested.

## What is secret, and where it lives

| Item | Where | Never |
|---|---|---|
| GitHub access token | Memory of the open tab; optionally `sessionStorage` if the owner ticks "keep me signed in while this tab is open" | `localStorage`, IndexedDB, cookies, the repository, the built site, URLs, request bodies, error messages, the console |
| Repository owner/name/branch, interface language, and the word goal of each article (`abdo.goal.<id>.<language>`, a number) | `localStorage` | (not secret) |
| Unpublished changes (drafts, uploaded images) | IndexedDB in this browser, keyed by repository | Encrypted: they are **not** |

Inside the code the token is held in a closure, not an object property, so logging or serialising the store object cannot reveal it. It is sent only in the `Authorization` header to the configured API origin, with `credentials: 'omit'`, `referrerPolicy: 'no-referrer'` and `cache: 'no-store'`. Errors are written from fixed text and GitHub's own `message`, never from the request.

## Threats and what was done

| Threat | Mitigation | Tested |
|---|---|---|
| A stranger uses the admin | They can open the page but have no token; GitHub rejects every write. The page is `noindex`, disallowed in `robots.txt`, absent from the sitemap and not linked from public pages | Yes (build tests, browser test) |
| Token theft by injected script (XSS) | No `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `eval` or `new Function` anywhere in the admin; all text goes through text nodes. A strict CSP meta tag: `default-src 'none'; script-src 'self'; style-src 'self' blob: https://fonts.googleapis.com; font-src https://fonts.gstatic.com; img-src 'self' blob:; frame-src blob:; connect-src 'self' <api origin>; base-uri 'none'; form-action 'none'`. Scripts are `'self'` only and there are no inline style attributes, so the style sources added in Phase 3 (below) cannot run code. | Source scan test; browser test reports zero CSP violations |
| Hostile content in an article reaching the admin through the preview (Phase 3) | The preview is drawn by the build's renderer, which escapes all text and allows only the inline markup listed in [editor.md](editor.md); it is shown in an `<iframe sandbox="allow-same-origin">` from a `blob:` URL. There is **no** `allow-scripts`, so even markup that slipped through could not run code, and the frame has no access to the token (which lives only in the admin page's memory). `allow-same-origin` is there so the page's own generated stylesheets and images load; it is safe only because scripts are off | Unit tests with hostile input; browser test checks the sandbox attribute and that nothing runs |
| Hostile text pasted into the editor (Phase 3) | Inline markup is parsed by a small fixed grammar; links accept only `https:`, `http:`, `mailto:`, `tel:`, site paths and `#anchors` (`javascript:` and `data:` are refused); unknown block types and fields are rejected by the validator | Markup and validator tests |
| Hostile or oversized files pasted, dropped or picked into the editor (Phase 3 follow-up) | Every route uses the Media screen's upload flow: the file is inspected by its bytes (PNG, JPEG, GIF, WebP only, size and dimension limits), the browser's reported type and the file name are not trusted, the name is made safe and unique, and the owner must describe the picture in every language before it is added. A paste is intercepted only when the clipboard holds a picture and no text. Nothing is uploaded to GitHub until Review & publish | Unit tests of the byte inspection; browser test with a fake picture (`<script>` bytes named `.png`), a text file, cancel, and a real picture |
| A schedule that fails at the moment it matters (Phase 3 follow-up) | Scheduled content is validated as strictly as published content, so a mistake is an error when it is scheduled, not a failed timer run later; the timer workflow only reads the repository and deploys, with the same permissions as the existing deploy (no new secrets, no writes back to the repository) | Schedule tests (validation, injected clock, timer script, workflow file); the GitHub timer itself was not exercised |
| Third-party font requests (Phase 3) | The admin CSP allows `fonts.googleapis.com` and `fonts.gstatic.com` and nothing else, only so the typography preview can show the fonts the site would load. Every visitor's browser contacts Google for those fonts on the public site too; choosing a *System fonts only* pairing removes that | CSP in the browser test; font loading itself was **not** verified (blocked in the test environment) |
| Hostile or broken values written into generated CSS (Phase 4) | Colours must be `#rrggbb`; sizes must be plain lengths (`px`, `rem`, `em`, `ch`, `vw`, `%`) checked by the schema, by the validator (characters such as `{ } ; < > \\`, `url(`, `@import` are refused) and again by the generator, which ignores anything that is not a plain length or a sane column count instead of writing it. Fonts are chosen from a fixed list whose stacks and Google Fonts requests are written in code, so the Studio cannot produce a request to an arbitrary host; a hand-edited stack is validated like any other value. The Studio's own screens set colours with the CSSOM, never an inline `style` attribute, so the admin CSP is unchanged | Layout, fonts, contrast and build tests; browser test (zero CSP violations) |
| Unreadable design published by mistake (Phase 4) | Text below 3 : 1 contrast is a validation **error**, so the admin cannot publish it and the build fails; 3 to 4.5 : 1 and Glass Mode readability are warnings | Contrast tests; browser test (publish is disabled until Fix) |
| Visitors contacting a third party (Phase 4) | Each font in the Typography Studio is labelled *Google* or *system*; a language on system fonts has no Google Fonts link at all | Fonts tests; browser test builds both |
| Script or data links in content (Phase 5 fix) | The validator's `uri` format used to accept any `scheme:` text, so `javascript:` and `data:` links were valid in profile links, project links, canonical URLs and navigation. It now accepts only `http:`, `https:`, `mailto:` and `tel:` addresses without spaces; the navigation editor flags a bad address as you type. Inline links inside article text already had this rule | Tests for four places with six bad and four good addresses each; browser test |
| Hostile text reaching a visitor through search (Phase 5) | The public search script builds results, snippets and suggestions with text nodes and `textContent` only (matches are wrapped in `<mark>` elements it creates itself); the index holds data, never markup. The query comes from the address bar, so it is length-limited, the page number is bounded and filters are checked against the index's own lists. Search settings are validated; synonym words cannot contain spaces | Build test of the shipped script; browser test types markup into the box and checks it is shown as text |
| Hostile values in topic accent colours (Phase 5) | Colours are `#rrggbb` (schema and validator); the stylesheet rule's class name is made from the digits only; the site and preview use classes, not inline styles, so the admin CSP is unchanged | Unit and build tests; browser test (zero CSP violations) |
| Private labels leaking through search or topic pages (Phase 5) | The index and the pages are built from the public model: drafts, private tags and topics, unpublished languages and hidden blocks are absent from the index, the pages, the sitemap and the redirect pages | Build tests read the built files |
| Token sent to the wrong place | The API origin is validated (`https://host[:port]`, no path) and is the only `connect-src`; owner, repo and branch are validated before any request | Yes |
| Token left behind | Sign-out clears memory and `sessionStorage`; nothing else ever holds it | Yes (browser test step 19) |
| Token with too much power | The admin asks for, and documents, a fine-grained token limited to one repository with Contents read/write. It cannot verify the token's scope: GitHub does not reliably report it, so this is guidance, not enforcement | Not enforceable |
| Writing outside `content/` | The store refuses any path outside the content folder (`..`, `.`, absolute, odd characters) before sending a request | Yes |
| Malicious or corrupt upload | Type decided from magic bytes (PNG/JPEG/GIF/WebP) — the file name and the browser's reported type are ignored; image header must parse; 8 MB and 12 000 px limits; **SVG is refused** because it can carry script; stored names are reduced to lowercase ASCII with the extension of the *detected* type | Yes |
| Overwriting someone else's change | Expected-head check, per-file base versions, and a non-forced branch update; conflicts need an explicit choice | Yes |
| Publishing broken content | Same validator as the build; publish is blocked on errors; the GitHub Action's own build is a second gate and a failed build leaves the previous site live | Yes |
| Accidental publish | Review screen lists every file; nothing is sent before "Publish" | Yes |

## Known weaknesses (not fixed)

1. **A public repository exposes everything in it**, including drafts, private CV entries and hidden blocks. The build excludes them from the *site*, but `content/` is readable on GitHub. The admin shows a warning on the overview when it detects a public repository. If drafts must stay private, use a private repository (check GitHub's current plan rules for Pages from one) or keep them out of the repository.
2. **Local drafts are readable by anyone with access to the browser profile.** Signing out removes the token but keeps the unpublished changes so work is not lost; they are restored the next time you sign in to the same repository. On a shared computer, use **Discard all changes** before signing out, or clear the site's data in the browser.
3. **A stolen token is a stolen publisher.** Anyone holding it can change the repository's contents until it expires or is revoked. Use a short expiry, one repository, and revoke it in GitHub if a device is lost.
4. **XSS is mitigated, not impossible.** If a browser extension or a future bug injected script into the admin origin, the token in memory could be read. The CSP and the no-HTML-strings rule reduce the likelihood; they do not remove the risk. GitHub Pages cannot send real HTTP security headers, so the CSP is a `<meta>` tag (which cannot enforce `frame-ancestors`, so clickjacking protection is not available).
5. **No second factor on publishing** beyond GitHub's own login for creating the token.
6. **Not tested against the real GitHub API** and not penetration-tested. The tests use a local fake of GitHub.
7. **Branch protection can block publishing.** If `main` requires pull requests or status checks, GitHub will normally refuse the direct commit; the admin shows GitHub's message but has no pull-request mode.
8. **Scheduled text and internal notes are readable in the repository.** A scheduled page is hidden from the *site* until its date, and an article's internal notes never reach the site, but both are ordinary JSON in `content/`; in a public repository anyone can read them. The admin says so next to the notes box; the validator warns when a note looks like a password or token. Do not schedule, or write notes about, anything that must stay secret before its date.

## Rules for contributors

- No credential, token or private key in `content/`, `public/` or `src/`. A test scans the built site and the admin source for GitHub token patterns.
- No dynamic HTML in the admin. Use `h()` and text nodes from `public/admin/js/dom.mjs`.
- New network calls go through `GitHubStore` only; new storage keys must be listed in `public/admin/js/session.mjs` and in the table above.
